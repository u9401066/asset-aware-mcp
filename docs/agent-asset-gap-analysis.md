# Agent 資產能力與缺口分析

更新：2026-09-21。正式版維持 **1.4.0**；本文件將 main 上的 Unreleased
能力與仍在開發的工作分開，下一次整合發版使用 **1.4.1**。

## 專案的存在價值

若使用者只需要上傳文件、摘要或問答，模型內建文件分析可能已足夠。
我們需要證明的價值，是 Agent 能否持續操作原始文件並交付可核對的結果：
來源是哪一版、改了哪個元件、其餘內容是否保留、判斷依據在哪裡，以及
下次換模型或換工作階段後，這些資料是否仍能使用。

MCP 協定、PDF 拆頁、OCR 或 Markdown 轉換，各自都不足以構成差異。
較有價值的整合是：**原生文件操作、可回溯的證據、可重用的知識庫，以及
能讓 Agent 發現錯誤並修正的操作結果**。這是產品方向，仍須透過實際工作
與對照評估證明，不能把功能清單當成競爭優勢的證據。

例如掃描表格某格是 `007`：Agent 查看原圖後建立保留前導零的 XLSX 字串格，
並記錄來源頁面／區域與目標儲存格的版本。人類之後改成 `008`，舊的引用仍
指向當時的 `007`，新的內容必須重新核對。Wiki 可以串連判讀與來源，原檔和
舊版證據都留存。這比一次性的文字回答多了可檢查、可延續的工作結果。

## Agent 所理解的 asset

檔案成為資產，需要穩定身分、不可變版本、原生定位、可讀表示、可用操作、
關係及來源。PDF 頁面／區域、Word 段落／表格、Excel 儲存格、投影片圖形都
可以是資產元件；元件不是脫離原檔的文字片段。

原檔位元組是保存依據。文字、表格、PNG 預覽與 Wiki 是不同用途的表示。
轉出 Markdown 成功不代表原生格式可完整回寫；雜湊相符也不代表語意正確。

| 責任 | MCP 的必要檢查 | Agent 的核對與修正 |
|---|---|---|
| 來源 | 檔案／版本雜湊、定位與完整引用 | 是否選對文件、版本與證據 |
| 修改 | 過期／封存檢查、操作範圍、原生結構與回讀 | 修改意圖、文字／數值、依賴關係 |
| 外觀 | 提供實際預覽、呈現引擎資訊與檢查結果 | 裁切、遮擋、字型、分頁、色彩 |
| 引用 | 固定來源版本、選取範圍、自訂／CSL 顯示契約 | 文獻資訊與論述是否受到支持 |
| Wiki | 不可變來源快照、wikilinks、保留人類筆記 | 整理主張、關係、矛盾與更新需求 |

這個分工遵循使用者確認：MCP 提供必要檢查，Agent 負責完整核對與修正。
MCP 不具備通用語意判斷能力，也不應自行宣稱已完成完整視覺驗證。

## 目前能力：以操作與限制描述

以下依目前原生契約、實作與回歸測試整理。main 的 Unreleased 能力不等同
已安裝的 1.4.0；執行時應讀取完整 contract／schema 與 enabled flags。

| 格式／工作流 | main 已有能力 | 明確限制或後續工作 |
|---|---|---|
| PDF | ingest／拆解、頁面讀取與預覽、組合／排序／刪除、區域證據、支援種類的批註 CRUD、來源快照與 Wiki | 掃描語意由 Agent 判讀；不是任意排版重建或 PDF 內文編輯器；簽章、表單及複雜物件有保護限制 |
| DOCX／DFM | 獨立建立、區塊／表格讀寫、表格結構與版面、頁首頁尾與註腳／尾註、實際頁面預覽、證據與 Wiki | 只在已建模的操作範圍內保護格式；複雜欄位／修訂／依賴與 Word 分頁一致性仍須檢查 |
| XLSX／XLSM | 獨立 XLSX 建立、型別儲存格、工作表／格線／Table 操作、A2T 對應、版面與試算表呈現、證據與 Wiki | XLSM 支援依操作契約而異；不等同 VBA 編輯器或所有 Excel 公式／物件皆受支援 |
| CSV／TSV | 明確方言與編碼、字串欄位及列欄 CRUD、保留未修改位元組、引用與 Wiki | 不推測標頭、數值型別或公式；顯示與解釋由 Agent 核對 |
| PPTX | 獨立建立、投影片／支援圖形／表格／圖片操作、整頁預覽、原生引用與 Wiki | 複雜依賴會限制操作；靜態 Impress 預覽不是 PowerPoint 動畫或外觀一致性的證明 |
| 獨立 PNG／JPEG／TIFF／GIF／WebP／BMP／AVIF | 內部圖片核心已有影格／區域、方向／精度／metadata 檢查、預覽、衍生檔、TIFF 組合及候選版本檢查 | **尚未接入 MCP／引用／Wiki**；不是已公開的完整圖片工作流；解碼器未建模的圖層／私有資料由原檔保存 |
| DOC／ODT 等轉換入口 | 既有轉換流程可作特定文件的前處理 | 轉換後 DOCX 的能力不能等同原格式可逆 CRUD；不提供通用保真百分比 |
| HTML／EPUB／EML／MSG／LaTeX／其他格式 | 可保存檔案身分及原始位元組，部分上游工具有讀取能力 | 本專案尚未完成各格式的原生結構 CRUD、引用與 Wiki 契約 |

詳細操作見 [Native File Assets](wiki/Native-File-Assets.md)、
[規格](spec.md)、[Roadmap](../ROADMAP.md) 與
[圖片核心規格](native-image-spec.md)。

舊版分析中的「DOCX 100% round-trip」、「DOC／ODT 94.5%」及「缺口占企業
文件 30–40%」沒有在此文件中提供可重現的測量方法，因此移除。
不再用未定義分母的百分比描述格式覆蓋率或理解深度。

## 可參考的 GitHub 專案

這些專案提供不同層次的能力，應按需求組合。功能描述依各專案官方文件；
「可借鏡」欄是本專案的設計判斷，並不表示全部已整合或完整評測。

| 專案 | 官方提供的能力 | 我們可借鏡的部分 |
|---|---|---|
| [Docling](https://github.com/docling-project/docling) | 多格式解析、PDF 版面與表格、統一文件表示、OCR 與 MCP | 解析 adapter、結構／定位輸出、多格式測試資料；本專案已有 Docling adapter |
| [PyMuPDF](https://github.com/pymupdf/PyMuPDF) | PDF 讀取、擷取、呈現與操作 | 原生頁面／批註及實際 PNG 核對；本專案已有使用 |
| [pikepdf](https://github.com/pikepdf/pikepdf) | 以 QPDF 為基礎的 PDF 讀寫 | 物件／資源關係、結構檢查與組合策略 |
| [pypdf](https://github.com/py-pdf/pypdf) | 純 Python 的拆分、合併、裁切與頁面轉換 | 頁面操作契約、異常文件與互通測試；不能用它代替視覺核對 |
| [pdfplumber](https://github.com/jsvine/pdfplumber) | 字元、線條、矩形、文字與表格擷取 | 位置資訊及表格擷取結果的可視化核對 |
| [OCRmyPDF](https://github.com/ocrmypdf/OCRmyPDF) | 對掃描 PDF 加入可搜尋的 OCR 文字層 | OCR 作為衍生版本，保留原圖與轉換記錄 |
| [Pillow](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html)／[libvips](https://github.com/libvips/libvips/blob/master/doc/multipage-and-animated-images.md) | 圖片格式與多頁／動畫處理 | 影格、EXIF、色彩／精度與 metadata 的明確邊界；新圖片核心使用既有 Pillow 依賴 |

不用重寫所有解析器。我們要補齊的是來源身分、可控修改、完整回讀、Agent
核對流程，以及長期可用的引用／Wiki。上游解析得更好時，應能替換 adapter，
而不必丟棄已有的原檔與歷史證據。

## 下一步與驗收方式

1. 完成獨立圖片從核心到 MCP、證據、Wiki 的整條流程，保持舊能力相容。
2. 使用真實文件與實際 Codex MCP 操作，保留失敗紀錄；將結構檢查、圖片
   核對及語意判斷各自記錄，不能把程序成功當成理解正確。
3. 增加轉換型格式時，先說清楚「唯讀解析／有損轉換／原生回寫」的範圍，
   再建立格式專用 adapter 與保護測試。
4. 對照模型內建文件分析、一般 coding Agent 搭配現成函式庫，以及本 MCP。
   用相同來源與任務比較正確交付率、來源可追溯率、未授權變更、失敗恢復、
   人工核對時間、延遲與 token 使用量。尚無同條件結果時，不宣稱本專案勝出。

原生修改後仍能找到舊證據、讓另一個 Agent 接手、並保持人類文件可用，才是
這個方向值得投入的實際驗收目標。「支援所有格式」仍是長期目標。
